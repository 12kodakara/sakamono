# 2台のPCで作業するときの決まりごと（自宅PC・会社PC）

このファイルは、**自宅PCと会社PCの2台**でサカモノを開発するための手順書です。
専門用語はできるだけ使わずに書いています。

---

## 0. いちばん大事な原則

> **正本（せいほん＝本物）は GitHub にあるものだけ。**
> PCの中にあるファイルは「GitHub の写し」だと考えてください。

この原則さえ守れば、どちらのPCで作業しても内容がずれません。
逆にこれを破ると（片方のPCにだけ変更を貯めると）、あとで直すのがとても大変になります。

**作業を始める前は必ず `git pull`、席を離れる前は必ず `git push`。** これだけです。

---

## 1. 2台の役割のちがい

| | 自宅PC | 会社PC |
| --- | --- | --- |
| Node.js | **使える**（v24） | **使えない**（インストール禁止） |
| `npm test` / `npm run build` | できる | **できない** |
| ソースの編集 | できる | できる |
| 画面で表示を確認 | できる（`npm run dev`） | **できない** |
| 検証の方法 | 手元で実行 | **GitHub Actions にやらせる** |

> ★会社PCに Node.js を入れたり、会社の制限を回避したりしないでください。★
> その必要はありません。検証は GitHub 側で自動的に行われます。

---

## 2. 自宅PCでの手順（従来どおり）

```bash
# 1. 最新を取り込む（作業前に必ず）
git pull

# 2. 編集する

# 3. 手元で検証する
npm test
npm run typecheck
npm run build

# 4. 変更内容を目で確認する
git status
git diff

# 5. 保存して送る
git add -A
git commit -m "わかりやすい説明"
git push
```

初めて自宅PCを使う日は、`npm ci` で必要なライブラリを入れてください。

---

## 3. 会社PCでの手順（Node.js なし）

```bash
# 1. 最新を取り込む（作業前に必ず）
git pull

# 2. 編集する（Claude Code で編集してもらってよい）

# 3. 変更内容を目で確認する ← ここが手元の検証の代わり
git status
git diff

# 4. 保存して送る
git add -A
git commit -m "わかりやすい説明"
git push

# 5. GitHub の Actions タブで、緑のチェックが付くまで待つ
```

**GitHub Actions が、自宅PCの代わりに次を全部やってくれます。**

1. `npm ci`（ライブラリの用意）
2. `npm test`（テスト）
3. `npm run typecheck`（型の確認）
4. `npm run build`（サイトの組み立て）
5. 公開成果物に秘密情報が混ざっていないかの検査
6. GitHub Pages への公開

どれか1つでも失敗すると、**公開されずに止まります**。
つまり会社PCから壊れたものを push しても、公開サイトは壊れません。

> 赤い×が出たときは、Actions の画面でどのステップが落ちたかを見て、
> 直して commit → push をやり直してください。
> 自宅PCに戻れる場合は、自宅で `npm test` を実行したほうが原因が早く分かります。

**会社PCでやってはいけないこと**

- `npm` で始まるコマンドを実行しようとすること（Node.js が無いので動きません）
- 動かないことを理由に Node.js を入れる、または会社の制限を回避すること
- 「テストしていないけど大丈夫だろう」と、確認せずに大量の変更を push すること

---

## 4. 会社PCへ「コピーしてはいけない」もの

会社PCは `git clone` で用意します。**フォルダごとコピーしないでください。**
次のものは GitHub に入っていませんし、入れてもいけません。

| もの | 理由 |
| --- | --- |
| `.env.local` | **APIキーが入っています。** 持ち出さず、会社PCで手入力してください |
| `node_modules/` | 巨大です。`npm ci` で作り直すもの（会社PCでは不要） |
| `.next/` `out/` | ビルドで作られる一時ファイル |
| `.cache/` `external/` `normalized/` | 取り込んだ生データ。共有しません |
| `tsconfig.tsbuildinfo` | 型チェックの一時ファイル |

### 会社PCの初回セットアップ

```bash
git clone https://github.com/12kodakara/sakamono.git
cd sakamono
```

以上です。会社PCでは `npm ci` は実行できませんが、
**ソースの編集・commit・push はこれだけで行えます。**

---

## 5. APIキー（秘密情報）の扱い

- APIキーは `.env.local` にだけ書きます。このファイルは Git の管理対象外です。
- **このリポジトリは public（全世界に公開）です。** 一度 push すると、あとから消しても取得済みの人には残ります。
- キーを別のPCへ渡すときは、**GitHub を経由させないでください**（チャット・メール・コミットも不可）。
  パスワード管理ツールなど、別の安全な経路を使ってください。
- 会社PCで API 取得コマンド（`npm run data:*`）は使えないので、
  **会社PCに `.env.local` を置く必要はありません。** 置かないのがいちばん安全です。
- 値が空の雛形は `.env.example` にあります。必要になったらこれをコピーしてください。

## 6. 困ったときの対処

### `git push` が拒否された（rejected）

相手のPCから先に push されています。取り込んでからやり直します。

```bash
git pull --rebase
git push
```

### `git pull` で衝突（conflict）した

同じ行を2台で別々に直したときに起こります。落ち着いて、

```bash
git status          # どのファイルが衝突したか見る
```

を実行し、ファイルを開いて `<<<<<<<` `=======` `>>>>>>>` の部分を正しい内容に直してから、

```bash
git add <直したファイル>
git rebase --continue
```

を実行します。**迷ったら、その場で作業を止めて相談してください。**
`git reset --hard` や `git push --force` は、作業内容が消えるので使わないでください。

### 改行コードで全行が変更扱いになった

`.gitattributes` で防いでいるので、通常は起きません。
もし起きたら push せずに相談してください。

## 7. 使用する Node.js のバージョン

| 場所 | バージョン |
| --- | --- |
| GitHub Actions（正本の検証環境） | **22** |
| 自宅PC（現在） | v24.19.0 |
| `package.json` の `engines` | `>=22` |

自宅PCが 22 以上であれば問題ありません。
会社PCには入れません（入れる必要がありません）。
